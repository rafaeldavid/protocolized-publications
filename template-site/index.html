Protocolized · Meta-documentation

A Self-Documenting Report Template

Meta-documentation for a Protocolized report surface designed to serve both human readers and LLM agents as first-class consumer classes. The document you are reading demonstrates each of its own affordances; the body is literally an explanation of the page you're on.

Template · Updated 2026-04-20

Why this template exists

Documents on the web evolved against a single consumer class: a human reader at a pointer device. Navigation, typography, breakpoints, and analytics all assume that one reader.

A second consumer class now reads the same documents: LLM agents acting on behalf of humans. Agents read differently. They want canonical text, stable structure, and programmatic hooks. They annotate as they read. They compose notes from the document with actions taken elsewhere.

ConsiderationsConsumer classes. The distinction is developed in the APIs paper's Q7 — "What makes an agent a distinct consumer class?". Agents read faster, in parallel, at machine speed, with different patience envelopes than humans. A document that ignores the distinction serves the agent poorly.

A document built only for the human reader leaves the agent degraded: it scrapes text via brittle DOM extraction, guesses at structure, and cannot leave a trace of what it noticed. A document built only for the agent loses the human's preferred reading experience. Most public documents today sit in the first camp.

This template is a scaffold for documents that serve both consumer classes without subordinating either. It is intentionally modest — a single HTML file, a handful of patterns — not a framework.

How it differs from a standard web page

Most public reports, working papers, and blog posts default to a backend CMS, an analytics beacon, a publisher-hosted comment system, and visual chrome sized for a laptop screen. Each default makes sense in isolation; together they produce a page that is readable by agents only as a side-effect of being readable by humans.

This template makes the opposite defaults.

Affordances: paired gutters and a canonical source

The page exposes three visible text channels and two non-visual ones.

The visible channels:

  1. Main column — the document itself.
  2. 1The numbered reference sidenote follows the Tufte CSS / Gwern convention: a superscript number in body text pointing to a floating note in the right margin. Distinct from the orange Considerations aside (prose commentary, labelled); reference sidenotes are for citations and brief amplifications. See the APIs paper for extensive use of both variants on one page.
    Right gutter — Considerations, in orange. Author-written commentary, baked into the publish, immutable to the reader. A second variant lives in the same gutter: numbered reference sidenotes in purple, matching the Tufte/Gwern pattern.¹
  3. Left gutter — Comments, in blue. Reader- or agent-written annotations, stored in the reader's localStorage only. Never transmitted. A mirror of Considerations.

The non-visual channels:

  1. Embedded markdown source — at the bottom of the document body lives <script id="markdown-source" type="text/x-markdown">, carrying the full document as markdown. An agent can read this one element and has the canonical text without walking the DOM.
  2. Programmatic comment API — window.templateAPI exposes the comment operations. See the agent-API section below.

The agent API

Agents running in the reader's browser — devtools consoles, extension-based assistants, Claude Desktop with browser use — interact without any auth, backend, or network call. The page exposes a single global:

// Add a comment anchored to a paragraph id.
// quote must occur verbatim in the paragraph's textContent.
window.templateAPI.addComment({
  pid: "p-why-3",
  quote: "brittle DOM extraction",
  text: "Agent observation — the template addresses this via the embedded markdown source.",
  author: "claude"
});

// Other operations
window.templateAPI.listComments();
window.templateAPI.deleteComment(cid);
window.templateAPI.clearComments();
window.templateAPI.markdownSource();                       // raw body, no comments
window.templateAPI.exportMarkdown({ includeComments: true });
window.templateAPI.refresh();                              // re-render from localStorage
ConsiderationsSkills vs MCP vs this. This page is not an MCP server nor a Skill (as discussed in the APIs paper Q8). It is a document surface that happens to expose a JS API to any agent loaded in the same browser. The agent reaches it by reading the DOM, not by calling over a protocol.

Author attribution: pass author and the comment's label reads Comment · claude. Default is reader with no suffix.

Markdown roundtrip: exportMarkdown returns the embedded source plus a ## Reader comments section. Every comment becomes a block carrying its paragraph id, quote, author, date, and body. An agent can take the blob into a separate context window and resume working on the annotated document without re-reading the page.

What this template is not

  • Not a CMS. The canonical text sits in the HTML. There is no backend writing it.
  • Not a hosted comment system. Comments never leave the reader's browser. Two readers of the same URL see two independent comment sets.
  • Not a knowledge base. There is no search, no cross-reference, no version history beyond the publish timestamp.
  • Not an agent harness. Agents can read and annotate; they cannot execute actions against external systems from this page. For that you would add tools, an MCP server, or a CLI (see the APIs paper Q8).
  • Not tracked. No analytics, no beacons, no third-party scripts beyond the font CDN.

Improvement backlog

The current implementation ships all capabilities that are achievable inside a single static HTML file. Items below that require external components (a server, a build step, an MCP endpoint, a shared site manifest) are documented here as open backlog for anyone forking the template to implement.

Shipped (in-page, no external components)

  • Agent discovery metadata. <meta name="agent-api">, <link rel="alternate" type="text/markdown">, and a Schema.org Article JSON-LD block in <head>. Agents scanning the first KB of markup find the API entry point, the markdown source location, and a structured document descriptor without walking the DOM.
  • Sibling markdown file. The same source embedded in <script id="markdown-source"> is also served as /template/index.md. Agents can fetch("./index.md") and get plain markdown in one request.
  • W3C Web Annotation export. templateAPI.exportAnnotations() returns the reader's Comments as a JSON-LD Web Annotation Data Model collection, interoperable with Hypothes.is, note-taking apps, and other annotation-aware consumers.
  • Machine-readable API schema. templateAPI.schema() returns a JSON Schema describing every method's input and output — including the CommentRecord shape. Also exposed as a static <script type="application/json" id="template-api-schema"> block for zero-JS consumers.
  • Machine labels on annotations. Each aside in the document carries data-role (consideration · reference · reader-note) and data-author-class (author · reader · agent · template). An agent can query "all citations" or "all author commentary" via CSS selectors, no NLP needed.
  • Immutable origin field. Every stored CommentRecord carries origin: "ui" | "api" | "demo", stamped by the runtime (not by the caller). An agent cannot spoof its way into appearing as a human UI action.
  • Event bus. templateAPI.on(event, callback) supports comment:added, comment:deleted, comments:cleared. Returns an unsubscribe function. Another agent (or an extension) can observe without polling.
  • Cross-tab sync. Comments added in one tab appear in other tabs of the same origin on their next render, via the storage event. No polling, no websocket.
  • Document hash. templateAPI.docHash() returns a SHA-256 digest of the embedded markdown source, computed at runtime. Agents can cache this hash across sessions and detect if the underlying document has changed.
  • Accessibility baseline. prefers-reduced-motion honoured; :focus-visible rings on all interactive elements; toast is a live region (role="status" aria-live="polite").

Open (requires external components)

These items would close genuine gaps in the agent-first design but can't be implemented inside a single static HTML file. A forker wanting a production-grade agent surface should consider them.

  1. Origin-level /llms.txt manifest at npc.here.now/llms.txt, enumerating every published document with its URL, title, topic tags, and agent-API version. See llmstxt.org for the emerging convention. Requires write access to the origin root, not just a per-document subpath.
  2. Site manifest at .well-known/protocolized.json — same substance as /llms.txt but JSON-LD, listing all documents with their canonical URLs, markdown-source URLs, and API schemas. Enables cross-document aggregation by agents ("find every Protocolized report on MCP and list the agent-authored Comments across them").
  3. MCP server wrapping the same capability. Expose read_document, list_annotations, add_annotation as MCP tools; the browser-resident window.templateAPI becomes a local specialisation of the same protocol. Required to make the template a genuine worked example of its own §What-this-is-not framing (which references the APIs paper's Q8). Could be a Cloudflare Worker, a Vercel function, or a self-hosted Python/Node process.
  4. Build step to eliminate MD/HTML drift. The embedded markdown source and the <article> body are maintained by hand today; the critique calls out the drift risk. A ~50-line build script (markdown-it or similar) taking a canonical .md file and emitting the HTML body + embedded source would fix this. Tradeoff: introduces a toolchain the template currently avoids.
  5. ?mode=agent stripped-chrome variant. Serve a minimal HTML shell (no banner, no title block, no comment form, no sections overlay) when ?mode=agent is present, cutting page weight by ~80%. Requires server-side routing; static hosting alone can't dispatch on query strings. Alternative: accept the cost and point agents at index.md.
  6. TextQuoteSelector with prefix and suffix context. Current anchoring finds the first occurrence of quote in the target paragraph. If text drifts (edit → re-publish), the anchor silently fails. Adopting W3C's full TextQuoteSelector with surrounding context would let comments re-anchor through modest edits. Doable in-page but adds complexity; left as a v2 improvement.
  7. Agent-as-co-author flow. The current roles are author (writes Considerations), reader (reads), agent (annotates). A deeper mode: agent writes a summary of the document, human approves/edits, the summary becomes a new Consideration. Requires new UI (summary-draft slot, approve/reject interactions) and a storage model for pending author-edits. Significant design scope.
  8. Signed agent identity. origin is stamped by the runtime and cannot be spoofed — but author is a free-text string. A malicious agent could still claim author: "claude" or impersonate a specific user. A session-key signing scheme where the runtime verifies a signature before accepting the comment would close this. Out of scope for a reading surface; relevant if the template is used in trust-sensitive contexts.

How to contribute an improvement

Fork the source from rafaeldavid/protocolized-publications/template-site (or grab the page directly via fetch — it's one self-contained HTML file). Pick an item from the open list, implement, republish via publish.sh. If the improvement is reusable, consider upstreaming by opening a discussion on the Protocolized forum.

Forking and reuse

The entire template is one HTML file per page. Styles, scripts, banner, favicon, and markdown source are all inline or embedded. To repurpose for a new report:

  • Replace the <article> body and the <script id="markdown-source"> contents. Keep them in sync — the embedded source is the canonical text that agents read.
  • Give every anchorable block an id (semantic preferred: id="intro", id="tactical") so comments can target it reliably.
  • Update the banner SVG text, title block, breadcrumb links, and sections overlay.
  • Change STORAGE_KEY if you want a separate comment set per report.
  • For multi-page reports, copy /template/exercise/ as a subpage stub and flip the breadcrumb's active class per page.

Source lives at rafaeldavid/protocolized-publications/template-site. Publish via the here.now skill with publish.sh.
